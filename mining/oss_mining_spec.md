# OSS Repository Mining Specification

**Purpose**: Populate the D2 (OSS practice evidence) column of Rule Registry V0.1 for 43 rules by mining Twenty CRM and Cal.com source repositories and their PR review history.

**Status**: V1 — supporting tooling specification for the MSc dissertation experiment.

**Estimated duration**: 2–3 working days end-to-end.

**Target users**: The researcher operating Claude Code as a coding assistant for this mining task. NOT for the experimental measurement pipeline.

---

## 0. Purpose and Methodological Justification

The Rule Registry V0.1 includes a "D2 OSS practice evidence" column for each of its 43 rules, currently marked TBD. This specification defines a reproducible procedure for populating that column.

Two distinct evidence streams are gathered:

1. **Static repository state**: configuration files (ESLint, dependency-cruiser, tsconfig), documentation (CONTRIBUTING, ADRs), and the result of running the experimental harness's detection scripts against the OSS code itself. This answers: "Do these production-grade CRM/SaaS codebases conform to each rule?"

2. **PR review comments**: review feedback from merged pull requests over the last 12 months, thematically clustered and mapped to rules. This answers: "Which rules do senior reviewers actively enforce in code review, as opposed to merely declaring in documentation?"

The two streams are complementary. Static state reveals what the codebase looks like today; review comments reveal what reviewers fight to keep it that way. Wan et al. (2023) found that "some organizations rely heavily on periodical manual inspection ... inspectors rely on the detailed description of code changes" — meaning the social process of code review is often a better indicator of de facto rule enforcement than static documentation.

**This specification deliberately does NOT use OSS code as ground truth for "correctness".** It treats OSS as Tier-3 evidence (cf. Rule Registry V0.1 §2.3 source tier hierarchy): supporting evidence that strengthens or weakens rules already supported by Tier-1/2 sources, but never the sole basis for admitting a rule into V1.

## 1. Prerequisites (Before Starting)

The following decisions and setup must be completed by the researcher before invoking Claude Code for any stage. None of these can be delegated.

### 1.1 Pin Commit SHAs

For both Twenty CRM and Cal.com, record the commit SHA of the current `main` branch HEAD at the moment mining begins. These SHAs are immutable; the dissertation must reference them by SHA in all subsequent text and appendices.

```
twenty:  https://github.com/twentyhq/twenty       commit: 36e89c04ad160914d84e64ac1215b83a8c6a6c12
calcom:  https://github.com/calcom/cal.com        commit: 53e32a5bbad43b262a5e1fef37f57fc67738afdb
fetch_date: 2026-06-30
```

Save to `evidence/manifest.json` (see §2 file structure).

### 1.2 GitHub Personal Access Token

A Personal Access Token (PAT) with `public_repo` scope is required for PR review mining (Stage S4). Without it, the GitHub API rate limit is 60 requests/hour, which is insufficient.

- Generate at https://github.com/settings/tokens (classic or fine-grained, either works).
- Set `public_repo` scope only — no write access needed.
- Export via environment variable: `export GITHUB_TOKEN=ghp_...`
- **The token must NEVER appear in source code, prompt files, log files, or git commits.** This is the same discipline encoded in Rule Registry SEC-1 ("No hardcoded secrets").

### 1.3 Working Directory Setup

Create an isolated mining workspace, separate from the experimental measurement harness:

```
~/dissertation/
├── experiment/              # existing — DO NOT TOUCH
│   ├── harness/             # the evaluation harness with detection scripts
│   └── baseline/
├── mining/                  # NEW — this specification's scope

```

Record the environment at start:

- Node.js version (`node --version`)

- Git version

These go into `evidence/manifest.json` alongside the pinned SHAs.

## 2. Output File Structure

The complete output of mining produces this tree:

```
evidence/
├── manifest.json                         # pinned SHAs, dates, environment
├── twenty/
│   ├── config/
│   │   ├── eslintrc.json                 # the active ESLint config(s)
│   │   ├── dependency-cruiser.cjs        # if present
│   │   ├── tsconfig.json                 # root and per-package
│   │   ├── package.json                  # root and per-workspace
│   │   └── prettier.json
│   ├── docs/
│   │   ├── CONTRIBUTING.md
│   │   ├── README.md
│   │   ├── architecture/                 # any ADRs or arch docs
│   │   └── other_relevant.md
│   ├── findings/                         # one JSON file per rule
│   │   ├── ARCH-1.json
│   │   ├── ARCH-2.json
│   │   ├── ...
│   │   └── LLM-8.json
│   └── pr_reviews/
│       ├── raw.jsonl                     # one JSON object per review comment
│       └── pr_metadata.json              # PR-level data (state, author, merged_at)
├── calcom/
│   └── ... (same structure as twenty/)
└── synthesis/
    ├── clusters.json                     # PR-comment thematic clusters
    ├── cluster_to_rule_mapping.md        # human-validated mapping
    └── d2_summary.md                     # one row per rule, twenty + calcom evidence
```

Each `findings/<rule_id>.json` has this schema:

```json
{
  "rule_id": "WEB-1",
  "repo": "twenty",
  "commit": "<SHA>",
  "status": "conforms | violates | partial | n_a",
  "confidence": "high | medium | low",
  "evidence": [
    {
      "type": "code_finding | config_setting | doc_statement",
      "location": "packages/twenty-server/src/.../foo.controller.ts:42-58",
      "summary": "GET handler does not invoke repository write methods"
    }
  ],
  "notes": "Optional researcher annotation"
}
```

Each `pr_reviews/raw.jsonl` line:

```json
{
  "pr_number": 1234,
  "pr_url": "https://github.com/...",
  "pr_title": "...",
  "pr_merged_at": "2026-04-12T...",
  "comment_id": "...",
  "comment_author_handle": "octocat",
  "comment_body": "this should be in the service layer",
  "comment_path": "src/foo.ts",
  "comment_line": 42,
  "comment_created_at": "..."
}
```

Note: `comment_author_handle` is preserved in raw data only for de-duplication and per-reviewer pattern analysis; it must be stripped or anonymised in any published artifact.

## 4. Stage S2: Static Artifact Extraction

### Task

Extract configuration files and documentation from both repos into `evidence/<repo>/config/` and `evidence/<repo>/docs/`. The goal is to have all "rule-bearing artifacts" available offline without needing to navigate the full clone for later analysis.

### Inputs

- The pinned clones from S1.

### Outputs

For each repo:

- `config/` containing: `.eslintrc*` (all variants), `dependency-cruiser.cjs` if present, root and per-package `tsconfig.json`, root and per-workspace `package.json` (dev-dependencies and scripts sections especially), `.prettierrc*`, any `commitlint.config.*`.
- `docs/` containing: `CONTRIBUTING.md`, `README.md`, anything under `docs/architecture/`, `docs/adr/`, `decisions/`, or similar directory names. Also any markdown file at the repo root with "architecture", "convention", "style", or "guideline" in its name.
- `inventory.json` listing each extracted file with its path within the original repo, the SHA-256 of its content, and a one-line summary if available.

### Acceptance criteria

- Every file in `config/` and `docs/` has a corresponding entry in `inventory.json`.
- No file is empty.
- For Twenty, the file `packages/twenty-server/.eslintrc.json` (or its current equivalent) is present.
- For Cal.com, the file `.eslintrc.js` (or current equivalent) is present.

### Out of scope

- Do NOT interpret or summarise the contents semantically yet (that is S3 and S6).
- Do NOT extract source code files — only configuration and docs.
- Do NOT extract files from `node_modules`, `dist`, `build`, or `.next` directories.

## 5. Stage S3: Code-Level Rule Check

### Task

Run the experimental harness's detection scripts against both OSS repos and record per-rule findings. **The detection scripts MUST be the same scripts used in the experimental measurement pipeline.** Reimplementation for this stage is forbidden.

### Inputs

- The clones from S1.
- The experimental harness (assumed to live at `~/dissertation/experiment/harness/`).
- The Rule Registry V0.1 (`Rule_Registry_V0.1.docx` or its extracted JSON form).

### Outputs

- `evidence/<repo>/findings/<rule_id>.json` for each rule. If a rule's detection method is Tier B (semi-automated) or Tier C (manual), record `status: "n_a_for_static_scan"` with a note explaining that the rule will be evaluated via a different mechanism (e.g. via PR review evidence in S4–S5 only).

### Acceptance criteria

- Every Tier-A rule from the registry has a corresponding `findings/<rule_id>.json` for each repo.
- Each finding has: `rule_id`, `repo`, `commit`, `status` ∈ {conforms, violates, partial, n_a}, `confidence` ∈ {high, medium, low}, an `evidence` array (which may be empty for `conforms`), and a free-text `notes` field.
- The detection scripts in `experiment/harness/` are not modified (verify by `git status` in the experiment directory before and after).

### Out of scope

- Modifying detection scripts in any way. If a detection script fails to run on the OSS code, record the failure as `status: "n_a"` with `notes` explaining the failure, and surface it for researcher decision. Do NOT attempt to "fix" the detection script to make it work on OSS code — that breaks the experimental measurement contract.
- Installing OSS repo dependencies. Detection scripts operate on source files via AST tools (ts-morph, etc.), not via running the application.
- Performing semantic interpretation beyond the script's output.

## 6. Stage S4: PR Review Mining

### Task

Fetch merged pull requests from the last 12 months for each repo and extract review comments into JSONL.

### Inputs

- `GITHUB_TOKEN` environment variable
- Repo URLs from manifest

### Outputs

- `evidence/<repo>/pr_reviews/raw.jsonl` — one line per review comment
- `evidence/<repo>/pr_reviews/pr_metadata.json` — PR-level data: number, title, author, merged_at, additions, deletions, files_changed, review_comment_count
- `evidence/<repo>/pr_reviews/fetch_log.json` — for reproducibility: query times, rate-limit headers seen, total API calls, error count

### Acceptance criteria

- `raw.jsonl` is a valid JSONL file; each line parses; each line has the schema documented in SPEC §2.
- `pr_metadata.json` includes the same PR numbers referenced in `raw.jsonl` (no orphans).
- `fetch_log.json` confirms total API calls < (PAT rate limit × 0.9) to leave headroom.
- Sample size sanity: Twenty typically yields 500–2000 PRs in 12 months and 3000–15000 review comments; Cal.com similar. If sample size is far outside this range, report and pause.

### Out of scope

- Clustering or any analysis (Stage S5).
- Filtering by comment content (raw mining captures everything; filtering happens later).
- Anonymising fields (raw data retains usernames; anonymisation happens in S5/S6 outputs).

### Claude Code prompt template

```markdown

## Context
S1–S3 completed. This stage uses the GitHub GraphQL API to extract merged PRs

## Task

1. Query the GitHub GraphQL API for pull requests that are merged: true and

   comment_created_at.
4. Write PR-level metadata to evidence/<repo>/pr_reviews/pr_metadata.json.
5. Maintain a fetch_log.json with: start_time, end_time, total_api_calls,
   rate_limit_remaining_at_end, pages_processed, errors[].

## Constraints
- Use GITHUB_TOKEN from environment; never log, echo, or write it to any file.
  In particular, do not include it in the fetch_log.
- Use the GraphQL API (not REST) for cursor-based pagination over PRs and
  review comments to minimise total API calls.
- Implement exponential backoff on secondary rate-limit errors.
- Halt and surface for researcher decision if total_api_calls would exceed
  90% of the rate limit ceiling.
- Do NOT fetch issue comments, only review comments tied to PR diffs.
- Do NOT fetch PR descriptions/bodies — only review comments.

## Acceptance criteria
- raw.jsonl parses (every line is valid JSON, every record has all required fields).
- pr_metadata.json's pr_numbers ⊇ unique pr_numbers in raw.jsonl.
- fetch_log.json shows the run completed without crashing and stayed within
  rate limit budget.

## Out of scope
- Clustering, classifying, or summarising the comments
- Filtering by content
- Anonymising author handles
```

## 7. Stage S5: Comment Clustering and Rule Mapping

### Task

Group review comments thematically and map each cluster to one or more rules in the registry. This stage is **semi-automated**: clustering is automated; rule mapping requires researcher review.

### Inputs

- `raw.jsonl` files from S4 (both repos)

### Outputs

- `synthesis/clusters.json`: an array of clusters, each with: `cluster_id`, `theme_label` (one short phrase), `representative_comments` (3–5 examples, anonymised), `comment_count`, `repos_present_in`.
- `synthesis/cluster_to_rule_mapping.md`: a researcher-validated markdown document listing each cluster and the rule(s) it provides evidence for (which may be zero).

### Acceptance criteria

- Total clusters: 30–80 (too few = under-clustered; too many = over-clustered).
- Each cluster's `representative_comments` are anonymised (no `comment_author_handle`).
- Every cluster appears in `cluster_to_rule_mapping.md` with researcher annotation (even if "no rule match — code style discussion").

### Out of scope

- Embedding model training (use an off-the-shelf small model like all-MiniLM-L6-v2 or use the Claude API to do theme extraction with an explicit prompt).
- Inferring "the LLM violates this rule because OSS reviewers flag it" — that conclusion belongs to the dissertation Discussion, not to this artifact.

### Recommended approach

Two viable paths; pick one based on familiarity:

**Path A — Embeddings + clustering (more reproducible)**:
1. Use sentence-transformers `all-MiniLM-L6-v2` to embed each comment_body.
2. Run HDBSCAN with min_cluster_size=5.
3. For each cluster, ask the Claude API to produce a 5–8 word theme label given 10 sampled comments.

**Path B — LLM-led clustering (faster, less reproducible)**:
1. Sample 500 comments stratified by repo.
2. Feed in batches of 50 to the Claude API with the prompt: "Group these N comments into themes; return JSON of {theme, comment_indices}".
3. Manually merge themes that recur across batches.

Path A is preferred for the dissertation because it is fully reproducible from raw.jsonl. If choosing Path B, save the exact API calls and responses in `synthesis/llm_calls.jsonl`.

### Claude Code prompt template

```markdown
# Mining Stage S5: Comment Clustering

## Context
S4 produced raw.jsonl for both repos. This stage groups comments thematically
and labels each cluster.

## Task
1. Load both raw.jsonl files (twenty + calcom).
2. Deduplicate exact-text comments while preserving counts.
3. Embed each unique comment_body using sentence-transformers all-MiniLM-L6-v2.
4. Cluster with HDBSCAN (min_cluster_size=5, metric=cosine).
5. For each cluster, sample 10 random comments and call the Claude API to
   generate a 5–8 word theme label. Save the API request/response to
   synthesis/llm_calls.jsonl for reproducibility.
6. Write synthesis/clusters.json with the schema in SPEC §7.
   ANONYMISE: representative_comments must exclude comment_author_handle.
7. Generate a draft synthesis/cluster_to_rule_mapping.md with each cluster
   listed, but leave the rule-mapping column blank for researcher to fill.

## Constraints
- Total cluster count target: 30–80. If outside this range, adjust HDBSCAN
  parameters and re-cluster up to 3 attempts; then surface for researcher.
- Do NOT include comment_author_handle in any output of this stage.
- Save embeddings and cluster assignments to synthesis/embeddings.parquet so
  the analysis is replayable.
- Do not fill in the cluster-to-rule mapping. That is the researcher's task.

## Acceptance criteria
- clusters.json validates and contains 30–80 entries
- All representative_comments are anonymised
- cluster_to_rule_mapping.md exists with all clusters but blank mappings

## Out of scope
- Inferring rule mappings
- Modifying raw.jsonl
- Drawing conclusions about LLM behaviour
```

## 8. Stage S6: Synthesis (D2 Column Fill)

### Task

Produce a single document, `synthesis/d2_summary.md`, that for each of the 43 rules summarises the combined evidence from S3 (static check) and S5 (PR clusters) into a single status with confidence and pointers to evidence.

### Inputs

- `findings/<rule_id>.json` × 43 × 2 repos
- `cluster_to_rule_mapping.md` (researcher-validated)
- The Rule Registry V0.1

### Outputs

- `synthesis/d2_summary.md` with one section per rule, structured:

  ```
  ### <RULE_ID> · <rule name>
  - Twenty: <status> (confidence: <h/m/l>). Evidence: <pointers>.
  - Cal.com: <status> (confidence: <h/m/l>). Evidence: <pointers>.
  - PR review evidence: <cluster IDs and themes that flag this rule>, or "none".
  - Combined D2 verdict: <one sentence>.
  ```

### Acceptance criteria

- All 43 rules have an entry.
- Each entry cites a specific location (file path with line range, or cluster ID).
- The Combined D2 verdict reflects researcher judgement, not an averaged automatic computation.

### Out of scope

- Modifying the rule registry itself (V0.1 → V1 happens AFTER this stage as part of the supervisor review).
- Generating "recommendations" — that belongs in the dissertation, not in this mining artifact.

### Claude Code prompt template

```markdown
# Mining Stage S6: Synthesis

## Context
All previous stages completed. This stage combines static findings and PR
cluster evidence into a single per-rule D2 summary document, which will be
used to populate the D2 column of Rule Registry V0.1 (yielding V0.2).

## Task
1. Load all findings/<rule_id>.json files for both repos.
2. Load synthesis/cluster_to_rule_mapping.md.
3. For each of the 43 rules, write a section in synthesis/d2_summary.md
   in the format specified in SPEC §8.
4. For "Combined D2 verdict", combine signals with this hierarchy:
   - If static finding = "violates" in both repos AND PR cluster also flags it
     → "Mature OSS does not consistently conform; this rule may reflect a
        stricter normative position than industry practice."
   - If static finding = "conforms" in both AND PR cluster flags it → "Mature
     OSS conforms; reviewers actively enforce this rule (corroborating evidence)."
   - If static finding = "conforms" in both AND no PR cluster → "Mature OSS
     conforms (silently, not actively reviewed)."
   - If split → "Mixed evidence; cf. detail above."
   - If n_a → "No direct OSS evidence available; rule supported by Tier-1/2
     literature only."
5. Mark the verdict as a DRAFT requiring researcher confirmation.

## Constraints
- Cite specific evidence locations (file:line for code findings; cluster_id for
  PR evidence). Generic statements without pointers are not acceptable.
- Use neutral language. Do not claim that OSS violations imply the rule is wrong.
- Anonymise: never include reviewer handles in this document.

## Acceptance criteria
- d2_summary.md has 43 sections, one per rule
- Every section has Twenty, Cal.com, PR-review, and Combined verdict subsections
- Every evidence citation is a specific path-or-id

## Out of scope
- Modifying Rule_Registry_V0.1.docx
- Drafting recommendations
- Making claims about LLM behaviour
```

### Anonymisation

Raw PR review data (raw.jsonl) retains `comment_author_handle` for de-duplication and per-reviewer pattern analysis only. All downstream artifacts intended for inclusion in the dissertation or supplementary material must strip handles:

- `synthesis/clusters.json` representative_comments: handles removed
- `synthesis/d2_summary.md`: no handles
- Any figure or quote in the dissertation: handles removed

### Token Hygiene

`GITHUB_TOKEN` must not appear in:
- Any committed file
- Any log file written to disk
- Any prompt sent to the Claude API
- Any error message that gets persisted

If a token leak is detected, revoke the token immediately at github.com/settings/tokens and rotate.

## 11. Appendix C: Common Pitfalls

### Pitfall 1: Claude Code modifies the experimental harness

If Claude Code finds that a detection script in `experiment/harness/` errors out on OSS code, it may helpfully "fix" the script. This silently breaks the experimental measurement contract. Mitigation: Stage S3 prompt explicitly forbids modification and requires `git status` verification before and after.

### Pitfall 2: Token in error messages

A common pattern: Claude Code writes an error log containing the failed HTTP request, which includes the `Authorization` header. Mitigation: explicit prompt-level prohibition, plus post-stage grep:

```bash
grep -rEi 'ghp_|github_pat_' mining/ && echo "TOKEN LEAK DETECTED"
```

### Pitfall 3: Rate limit exhaustion mid-run

5000 requests/hour is generous but not infinite. With per-PR pagination, a 2000-PR repo with 20 comments each can approach 200 API calls. Two repos in one run is fine. Mitigation: pace requests, save state between batches, and the fetch_log records the rate-limit remaining at each batch boundary.

### Pitfall 4: Over-clustering or under-clustering

HDBSCAN with default parameters often produces too many small clusters or one mega-cluster. Mitigation: prompt requires Claude Code to attempt re-clustering up to 3 times within the 30–80 target before surfacing for researcher.

### Pitfall 5: "Helpful" semantic interpretation

In synthesis, Claude Code may try to summarise PR comments by paraphrasing what they "mean". This loses fidelity. Mitigation: synthesis must cite specific cluster IDs and quote within ≤15 words, with the source comment IDs preserved.

### Pitfall 6: Forgetting which commit was scanned

After a few days, the researcher may forget whether the d2_summary reflects the original pinned SHA or an updated one. Mitigation: the manifest is the single source of truth; every output file should reference manifest's SHAs in its header.
